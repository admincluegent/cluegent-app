Cypress Interview Questions: Retry-ability and Reliable UI Tests

Prepare Cypress interview answers about command queues, retry-ability, intercepts and application state, with an original search-results test example.

How should you explain Cypress's command queue?

Cypress commands are scheduled and executed by its runner; they are not ordinary synchronous assignments returning the current DOM value. Explain how your assertions and callbacks participate in the chain. Trying to store the result of a Cypress command as if it were the final element can create misleading code. Describe the test's intended sequence first, then show how the chain expresses that sequence.

What retries automatically?

Queries and assertions can retry together while waiting for the asserted condition. Do not assume every command or arbitrary callback repeats in the same way. In an interview, identify which step searches for the current element and which step checks its state. Explain why a chain waiting for a visible result is different from reading a value once and comparing it outside the retrying assertion.

What does cy.intercept help test?

It observes or controls relevant network traffic so the test can coordinate with a request or simulate a response. Register the intercept before the action that triggers the request. State the method and route you intend to match and avoid accidentally intercepting unrelated traffic. A mocked response is useful for a deterministic error state, but an additional integration test is needed to verify the real service contract.

How do you keep test data predictable?

Create the state each test needs and avoid relying on shared records that other tests mutate. Separate authentication setup from the behavior under examination when that helps keep the test focused. Explain how accounts and backend fixtures are reset or uniquely identified. A clean browser alone does not guarantee that the server has no leftover orders or customers from a previous run.

How would you reduce brittle UI checks?

Assert the user-visible result and use stable locators appropriate to the application. Avoid tying every check to the exact number of nested elements or unrelated styling. When an action changes the DOM, query the current state rather than assuming a previous element remains attached. Explain how the test handles loading, success and error states. Distinguish an application failure from an assertion that ran before the outcome was available.

Worked example

Original example: entering a search term requests results from a service. Install the route intercept first, enter the term and wait on the relevant request alias when coordination is needed. Then assert that the expected result is visible. A successful request alone does not prove the UI rendered it correctly.

Add a controlled empty response and a controlled server error. Define distinct user-visible behavior for each. If the test only checks that a spinner disappears, it can pass when the application silently loses the result. Use an assertion that communicates the actual requirement.

Practice plan

Sketch a successful search test and a server-error test. Explain what each intercept matches, when it is registered and which assertion can retry. Practice a follow-up about why you still need a test against the real service after the mocked cases pass.

Frequently asked questions

Does Cypress retry every operation?

No. Understand the retry behavior of queries, assertions and other commands rather than treating the entire test as one repeating function.

Should every response be stubbed?

Use stubs for controlled cases and keep real integration coverage where a dependency's contract matters.
