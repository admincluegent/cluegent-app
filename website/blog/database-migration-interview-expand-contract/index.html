Database migration interview: change a field without breaking clients

For a database migration interview, explain which application versions must continue working while the schema changes. A correct database command alone does not establish a safe release. PostgreSQL documents table modifications; this exercise concerns the application rollout around a change.

Reviewed by Cluegent Editorial Team · Updated October 10, 2026

Discuss compatibility before writing the migration

For a database migration interview, explain which application versions must continue working while the schema changes. A correct database command alone does not establish a safe release. PostgreSQL documents table modifications; this exercise concerns the application rollout around a change.

The fictional case fits backend and platform interview preparation for English-speaking teams in Europe. Its sequence is a suggested design discussion, not a universal migration recipe. Confirm the database, deployment model, data size and operational constraints before recommending a production plan.

Split a display name while old clients remain active

The current application reads a display_name field. A new requirement introduces separate presentation fields, while an older application version remains active during rollout. Existing names cannot be reliably split by a simple space rule. Explain how you would introduce the new representation without destroying the original data.

State what the new fields actually mean and whether users must supply them. Do not infer personal naming structure from a string. Decide how old and new versions read and write during the transition, how incomplete records behave and what a rollback can recover.

Migration discussion plan
StageQuestion to resolve
ExpandCan the new representation exist alongside the original field?
TransitionWhich version writes which fields, and how are conflicts handled?
BackfillWhat can be derived safely and what needs user input?
VerifyWhich checks show compatibility and data consistency?
ContractWhen are old reads and writes demonstrably gone?

Preserve information while changing the representation

A worked answer might propose adding nullable fields while retaining display_name, then introducing application logic that handles incomplete new data. Explain that automatic parsing would be unreliable for this requirement. A user-confirmed update may be needed, and older clients still need a defined behaviour.

Discuss rollback before removing anything. Reverting the application may be possible during the additive phase, but dropping or overwriting original information changes the recovery options. Verify the proposed database operations and locking behaviour against the database version and deployment environment rather than promising a zero-risk migration.

Follow-up questions to test your reasoning

  • What happens when an old client updates the original field?
  • How will you detect incomplete new records?
  • At what point does rollback require data recovery rather than a code revert?

Check whether the plan names readers, writers and verification evidence at every stage. A list of migration commands with no compatibility story misses the central exercise. Identify the assumption most likely to make your proposed sequence unsafe.

Explain the transition using a version table

Draw rows for old and new application versions and columns for reads, writes and fallbacks. Walk through one record that has only old data and one that has confirmed new data. The table should expose any undefined behaviour before you discuss removing a field.

Frequently asked questions

What is expand-and-contract migration practice?

Discuss adding a compatible representation, transitioning usage, verifying the change and removing the old representation only after its dependencies are understood.

Is a code rollback enough after a destructive migration?

Not necessarily. Removing or overwriting data can require a separate recovery plan. Explain the boundary before release.
