Networking Interview Questions: DNS, TCP and Troubleshooting

Prepare networking interview questions about DNS, TCP, TLS, routing and latency with an original website-connectivity troubleshooting scenario.

What happens when you open a website?

Describe the stages rather than reciting every protocol field: resolve a hostname, establish an appropriate connection, negotiate security where needed, send a request and receive a response. Cached information and existing connections can skip some work. State whether you are describing an HTTP-over-TCP example; modern traffic may use other transports. The purpose is to explain which stage could fail and what evidence would identify it.

How is DNS failure different from connection failure?

DNS translates a name into information used to reach a service. A successful lookup does not prove that the service is reachable or healthy. Compare name resolution with connection establishment and the application's response. An incorrect record, blocked port and failed application produce different evidence. Avoid immediately changing DNS because a browser says the site is unavailable; first determine which stage actually failed.

What does TCP provide, and what does it not provide?

TCP provides a reliable ordered byte stream between endpoints. It does not define your application's message boundaries, guarantee that an application processed a request or provide encryption by itself. A successful write at one layer is not a business acknowledgment. Explain how timeouts and retries interact with application operations: retrying a payment requires more care than retrying a read-only request.

What is TLS checking during a secure connection?

In a typical HTTPS connection, TLS establishes an encrypted channel and authenticates the server using a certificate chain and hostname checks. A certificate error may involve expiry, hostname mismatch or trust configuration. Check the actual error and the device's clock. Do not recommend ignoring certificate verification as a production fix. Explain how you would distinguish handshake trouble from an HTTP error returned after the secure connection succeeds.

How would you investigate slow requests?

Separate name-resolution time, connection setup, network transfer and server processing. Compare affected locations and request types, and distinguish latency from available throughput. Collect evidence from an approved environment and avoid assuming that one successful ping proves an application is healthy. State what your measurement includes. A slow database query and a congested connection can look similar to a user while needing different fixes.

Worked example

Original scenario: employees can reach a service from office Wi-Fi but not from a home connection. Ask whether the service is meant to be private and whether a VPN is required. Compare DNS answers, the target address and connection results in both environments. If the connection succeeds but login fails, move to authentication evidence rather than continuing to change routes.

A good answer proposes the smallest next check and predicts the observation that supports it. It also distinguishes an intentional access restriction from an outage. Verify the final user journey, not just one intermediate diagnostic.

Practice plan

Draw the path from browser to application and label one failure at each boundary. Rehearse a two-minute investigation with no commands, then add the tools you would use in your environment. Explain what a successful DNS lookup, TCP connection and HTTP response each prove—and what they leave uncertain.

Frequently asked questions

Should I memorize the OSI model?

Understand the boundaries, but demonstrate how they help you isolate an actual failure. A troubleshooting explanation is more useful than a list alone.

Does a successful ping prove a website works?

No. It does not verify the website's application path, authentication, secure connection or response content.
