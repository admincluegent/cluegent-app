API integration interview: investigate a customer's duplicate records

For an API integration interview, clarify the intended behaviour and identify where the evidence comes from. A customer report such as 'the API duplicates data' does not establish whether the source export, mapping, retry behaviour or destination handling is responsible.

Reviewed by Cluegent Editorial Team · Updated October 10, 2026

Clarify the integration contract before proposing a fix

For an API integration interview, clarify the intended behaviour and identify where the evidence comes from. A customer report such as 'the API duplicates data' does not establish whether the source export, mapping, retry behaviour or destination handling is responsible.

This original customer-facing case suits integration, support engineering and solutions applicants to European international teams. It tests diagnosis and communication rather than endpoint trivia. Use synthetic records during practice and protect customer credentials in a real investigation.

Investigate a daily customer import

A fictional customer imports contact records each day. The destination now shows duplicates with similar names. The source file includes an external contact ID, but some rows have it blank. The client retries failed batches. The brief does not say whether the destination creates or updates a contact on each request.

Ask for the intended create/update contract, a redacted example and a correlation between input rows and destination IDs. Do not recommend matching by name without discussing collisions and the customer's actual identifier rules.

Integration investigation worksheet
QuestionWhy it matters
Which identifier is stable?Names may not uniquely identify a contact.
What does a retry contain?The same batch may be submitted more than once.
What happens when ID is blank?The intended behaviour may differ from normal updates.
What evidence can be shared safely?Credentials and real personal records are unnecessary for a synthetic reproduction.

Give the customer a precise next step

An illustrative response is: 'I need to confirm whether the import is expected to update by external ID or create a new record. Could we reproduce the issue with two synthetic rows, including one without an ID? I will trace the resulting destination IDs and the retry sequence before recommending a change.' This acknowledges the report without prematurely assigning blame.

For the engineering handover, include the agreed expected result, the smallest failing input, the request sequence and observed output. Explain missing information explicitly. A long transcript of customer emails is less useful than a reproduction that another person can run.

Follow-up questions to test your reasoning

  • What if the external ID changes between exports?
  • How would you distinguish a duplicate from two legitimate contacts?
  • What should happen when a batch partly succeeds?

Check that your suggested fix follows the actual contract. Adding retries, removing retries or deduplicating by name can all introduce problems if the underlying semantics are unclear. State what needs confirmation before changing behaviour.

Write two versions of the handover

Prepare a short customer update and a technical reproduction note. Keep the facts consistent but adjust the detail to the audience. Ask a partner to identify the next action from each note without additional explanation.

Frequently asked questions

How do I prepare for an API integration interview?

Practise clarifying the contract, creating a minimal synthetic reproduction and explaining evidence to both customers and engineers.

Should I blame retries when records are duplicated?

Treat retries as one hypothesis. Verify identifiers, create/update semantics and the actual request sequence first.
